# Why user space, part 2: kernel-shipping burden, stability, performance (researched 2026-11-20)

"Verified on page" = text returned from fetching the primary page/PDF (PDFs read with pdftotext where noted). "Secondary only" = search summary or news, page not read. Courtesy rule observed: no AFS-vendor material. (One search hit about an AFS SMB loopback was discarded on purpose.)

## A. The burden of shipping kernel code

### A1. Windows

- **Kernel-mode drivers need Microsoft signing via a dashboard account that needs an EV certificate.** Docs, "Driver Signing Policy" (page ms.date 2024-08-19, updated 2025-07-18): "Starting with Windows 10, version 1607, Windows will not load any new kernel-mode drivers which are not signed by the Dev Portal." and "an EV code signing certificate is required to establish a dashboard account." For production, "you should submit HLK/HCK test logs". https://learn.microsoft.com/en-us/windows-hardware/drivers/install/kernel-mode-code-signing-policy--windows-vista-and-later- . Verified on page.
- **Attestation signing is for testing, not retail.** "Attestation signed drivers that target retail audiences aren't published on Windows Update." Prereqs: Hardware Developer Program registration and "You must have an extended validation (EV) code signing certificate." Microsoft re-signs: appends a Microsoft SHA-2 signature, overwrites the customer's signatures, replaces the catalog. Page dated 2025-07-15 (updated 2026-04-14). https://learn.microsoft.com/en-us/windows-hardware/drivers/dashboard/code-signing-attestation . Verified on page. Note: the page gives no turnaround time. A documented submission duration was not found; do not state one.
- **Cross-signed driver trust removed, 2026.** Microsoft Tech Community (Windows IT Pro blog), dated 26 Mar 2026 (updated 22 Oct 2026): "the removal of trust for all kernel drivers signed by the deprecated cross-signed root program." Applies to Windows 11 24H2, 25H2, 26H1 and Windows Server 2025 in the April 2026 update; "All future versions of Windows 11 and Windows Server will enforce the new kernel trust policy." Only WHCP-certified drivers load by default; an explicit allow list covers reputable legacy cross-signed drivers. Evaluation mode first: enforcement after 250 hours and 3 restarts (Windows 11) or 250 hours and 2 restarts (Server 2025); if any cross-signed driver would fail, the period resets. (The post says the threshold changed from 100 to 250 hours with the 9 June release.) Stated reason: the old program's certificate handling "led to abuse and credential theft". https://techcommunity.microsoft.com/blog/windows-itpro-blog/advancing-windows-driver-security-removing-trust-for-the-cross-signed-driver-pro/4504818 . Verified on page.
- **Driver Quality Initiative (DQI), WinHEC, 14 May 2026.** Four pillars: Architecture, Trust, Lifecycle, Quality Measures. Architecture pillar "moves third-party drivers toward user-mode or Microsoft-authored class drivers" (page wording paraphrased by fetch; it mentions "enabling the third-party kernel mode driver transition to either user mode driver or Microsoft authored class drivers"). Trust: stronger partner verification and automated analysis. No crash statistics are given and no formal user-mode mandate. https://blogs.windows.com/windowsexperience/2026/05/14/raising-the-bar-together-introducing-the-driver-quality-initiative-at-winhec-2026/ . Verified on page. Do not call it a mandate.
- **Cloud-initiated driver recovery, 12 May 2026.** Microsoft can "proactively rolls back problematic drivers delivered through Windows Update"; manual validation May-Aug 2026, automatic inclusion targeted Sept 2026. Reason given: the old fix depended on partners shipping a new driver, so devices "may remain on a low-quality driver for an extended period." No statistics. https://techcommunity.microsoft.com/blog/hardware-dev-center/introducing-cloud-initiated-driver-recovery-for-windows-update/4519075 . Verified on page. Whether it reached automatic inclusion in Sept 2026 was not checked.
- **Vulnerable driver blocklist and HVCI.** Docs page (ms.date 2026-05-01, updated 2026-10-08): "Since the Windows 11 2022 update, the vulnerable driver blocklist is enabled by default for all devices"; it is enforced when memory integrity (HVCI), Smart App Control or S mode is active (except Server 2016); "HVCI is on by-default for most new Windows 11 devices"; "The blocklist is updated quarterly" plus monthly Windows updates. Blocking "can cause devices or software to malfunction, and in rare cases, lead to blue screen." Reason: "malicious actors are turning to exploit vulnerabilities in legitimate and signed kernel drivers". https://learn.microsoft.com/en-us/windows/security/application-security/application-control/app-control-for-business/design/microsoft-recommended-driver-block-rules . Verified on page. Not found: an authoritative list of "older drivers incompatible with HVCI" stats; do not cite a number.
- **Windows Resiliency Initiative follow-up (June 2025):** secondary only (Microsoft post https://blogs.windows.com/windowsexperience/2025/06/26/the-windows-resiliency-initiative-building-resilience-for-a-future-ready-enterprise seen only in search results; ghacks/heise coverage "antivirus out of the kernel"). Whether the Windows endpoint security platform is generally available by Nov 2026: not found.
- **Not found:** a Microsoft-documented submission turnaround time; a Microsoft figure for the share of crashes caused by drivers after 2003 (DQI blog gives none).

### A2. macOS

- **Apple platform security guide, "Securely extending the kernel"** (page text returned): "Kexts need to be explicitly enabled for a Mac with Apple silicon by holding the power button at startup"; "Rebuilding the AuxKC requires the user's approval and restarting of the macOS to load the changes into the kernel"; "it requires that the secure boot be configured to Reduced Security."; "By running in user space, system extensions increase the stability and security of macOS." Frameworks named: DriverKit, EndpointSecurity, NetworkExtension. https://support.apple.com/guide/security/securely-extending-the-kernel-sec8e454101b/web . Verified on page (the fetch returned quotes; no page date shown).
- **Startup Security Utility steps (Mac User Guide):** "the security policy must be changed to Reduced Security" before a legacy kext can be installed on Apple silicon; flow is Recovery, Startup Security Utility, Reduced Security, tick "Allows installation of software that uses legacy kernel extensions", authenticate as admin, restart. Reduced Security is described as one that "Allows any version of signed operating system software ever trusted by Apple to run." https://support.apple.com/guide/mac-help/change-security-settings-startup-disk-a-mac-mchl768f7291/mac . Verified on page.
- Kext deprecation wording, WWDC19 session 702, FSKit in macOS 15.4 and macFUSE FSKit backend: already in why-research.md section 4. Not repeated.
- **Not found:** an Apple page that says outright "kexts are removed". Apple's wording is "deprecated" (kext KPIs). MDM exceptions and notarization details were not fetched.

### A3. Linux

- **Module signing.** Kernel docs: the facility "cryptographically signs modules during installation and then checks the signature upon loading the module"; with enforcement (`CONFIG_MODULE_SIG_FORCE` or `module.sig_enforce=1`) "the kernel will only load validly signed modules for which it has a public key"; without it, unsigned modules load but "the kernel will be marked as being tainted". https://docs.kernel.org/admin-guide/module-signing.html . Verified on page. The page does not mention Secure Boot or lockdown.
- **Lockdown.** man-pages kernel_lockdown(7): "Only validly signed modules may be loaded (waived if the module file being loaded is vouched for by IMA appraisal)." https://man7.org/linux/man-pages/man7/kernel_lockdown.7.html . Verified on page for that sentence only. The fetch did not confirm "lockdown turns on automatically with Secure Boot"; that is a distro-specific behaviour (not verified here).
- **MOK and DKMS (Debian wiki).** "modules built using DKMS will be signed using a machine owner key (MOK)"; keys default to /var/lib/dkms/mok.key and mok.pub; `sudo mokutil --import /var/lib/dkms/mok.pub` prompts for a one-time password; "Afterwards reboot your system and follow UEFI's onscreen instructions to confirm the key enrollment." https://wiki.debian.org/SecureBoot . Verified on page. Distribution-specific (Debian), not kernel.org. Not verified: "DKMS rebuilds on each kernel update" (widely true; no primary page fetched).
- **GPL-only symbols.** Kernel docs "Linux kernel licensing rules": for `MODULE_LICENSE("Proprietary")`, "the kernel module loader refuses to link such modules against symbols which are exported with `EXPORT_SYMBOL_GPL()`", and such modules taint the kernel with the 'P' flag. https://docs.kernel.org/process/license-rules.html . Verified on page.
- **2025 symbol-export change (minor):** a 2025 series renamed `EXPORT_SYMBOL_GPL_FOR_MODULES` to `EXPORT_SYMBOL_FOR_MODULES`; the macro still carries the GPL tag; an early version tried to restrict the namespace to in-tree modules, later dropped. LWN: nothing enforces the in-tree-only intent. https://lwn.net/Articles/1029492 and https://patchew.org/linux/20250808-export._5Fmodules-v4-1-426945bcc5e1@suse.cz . Secondary only (search summary). Weak as evidence for the site; skip it.
- **No stable in-kernel interface:** see why-research.md section 5 (verified).

## B. Stability

- **CrowdStrike RCA, 6 Aug 2024 (PDF read with pdftotext).** "The new IPC Template Type defined 21 input parameter fields, but the integration code that invoked the Content Interpreter with Channel File 291's Template Instances supplied only 20 input values." (page lines: "The Content Interpreter expected only 20 values. Therefore, the attempt to access the 21st value produced an out-of-bounds memory read"; heading "A runtime array bounds check was missing for Content Interpreter input fields"; "This is not an arbitrary memory write"). Mitigations include runtime bounds checks and "Template Instances should have staged deployment". https://crowdstrike.com/wp-content/uploads/2024/08/Channel-File-291-Incident-Root-Cause-Analysis-08.06.2024.pdf . Verified on page (the first-sentence wording above is from lines 44-67; the exact "supplied only 20 input values" phrasing is my reading of lines 44-47 and 63-68, so quote the "expected only 20 values" and "21st value" lines instead).
- Microsoft 8.5 million devices, csagent.sys as a file system filter driver, "Kernel drivers provide the above properties at the cost of resilience.", Resiliency Initiative: already in why-research.md section 3.
- **GAO, 23 Sep 2024, "Cyber Resiliency: CrowdStrike Outage Highlights Challenges" (GAO-24-107733).** Says the failure "was caused by human error and not a cyberattack" and that agencies "do not always adequately address issues found in testing". It does not discuss the kernel. So it supports "testing and update rollout" lessons, not "kernel drivers are bad". https://gao.gov/products/gao-24-107733 . Verified on page. CSRB: no CSRB report on this outage found; do not cite one.
- **FUSE when the daemon dies.** Kernel docs: "The connection exists until either the daemon dies, or the filesystem is umounted." A hung user-space file system can be handled: kill the daemon, `umount -f`, or abort via the FUSE control filesystem ("Writing anything into this file will abort the filesystem connection... all waiting requests will be aborted an error returned for all aborted and new requests."); "Abort filesystem through the FUSE control filesystem. Most powerful method, always works." https://docs.kernel.org/filesystems/fuse/fuse.html . Verified on page. The kernel doc does NOT mention ENOTCONN or the text "Transport endpoint is not connected". That is standard errno behaviour (ENOTCONN) but not cited from a fetched page here; mark as "common knowledge, not verified on a page".
- **Not found:** a 2022-2026 study giving the share of crashes caused by third-party drivers on Windows/macOS/Linux. Do not state a modern percentage.
- A user-space bug can still corrupt the data it serves or hang apps that touch the mount; the doc's own deadlock section ("The solution for this is to allow the filesystem to be aborted") shows hangs exist. Keep the claim to "the machine does not crash", not "nothing goes wrong".

## C. Performance, fairly

### C1. Where in-kernel wins (classic numbers)

- **Vangoor, Tarasov, Zadok, "To FUSE or Not to FUSE: Performance of User-Space File Systems", FAST 2017.** Abstract: "performance degradation caused by FUSE can be completely imperceptible or as high as -83% even when optimized; and relative CPU utilization can increase by 31%." Paper body (pdftotext): worst case was random read with 32 threads, "up to -83% for StackfsBase and -28% for StackfsOpt" with small I/O; "on HDD ... overhead negligible"; one case went "within 2% of Ext4's performance" once the daemon's max-background limit was raised from 12 to 100. So -83% is the unoptimised stack on SSD with small random reads; the optimised stack was -28% in that case. Hardware is 2017-era; the code has changed. https://www.fsl.cs.stonybrook.edu/docs/fuse/fuse-performance-fast17.pdf and https://www.usenix.org/conference/fast17/technical-sessions/presentation/vangoor . Verified on page. A claim of "latency up to 4x" is from a search summary only; not seen in the fetched text.
- **RFUSE, Cho, Choi, Kwon, Kim, FAST 2024 (pp. 141-157).** PDF read with pdftotext: RFUSE (per-core ring-buffer channel) "reduces communication latency by 53%"; "2.27x higher throughput than FUSE in the random read workload"; "42% higher TPS" in one application benchmark (Figure 13b); "roughly 7% higher CPU usage" in one case; abstract: "comparable throughput to in-kernel filesystems on high-performance devices". These are RFUSE vs stock FUSE and ext4 on fast NVMe with many cores, which is the stress case; RFUSE is a research kernel, not mainline. https://www.usenix.org/conference/fast24/presentation/cho and https://usenix.org/system/files/fast24-cho.pdf . Verified on page. The paper says the stock FUSE stack has "notable performance overhead" on modern hardware, which is a point against FUSE.

### C2. How the gap is closing (mainline)

- **FUSE passthrough, Linux 6.9 (2024).** KernelNewbies, Linux 6.9: "This release adds a passthrough mode for regular file I/O"; reads and writes, including mmap, go to a backing file without a trip to user space; "only privileged servers can use it". Kernel docs: "FUSE (Filesystem in Userspace) passthrough is a feature designed to improve the performance of FUSE filesystems"; covers read/write, splice, mmap; setup needs CAP_SYS_ADMIN; no benchmark figures on the page. https://kernelnewbies.org/Linux_6.9 and https://docs.kernel.org/filesystems/fuse/fuse-passthrough.html . Verified on page. Pre-merge Phoronix claim that it is "much closer to native" is secondary only. Limitation for the site: passthrough helps when the data lives in a local backing file, e.g. a local cache file in a caching client, which is the AFS case; it does not help the network read path.
- **FUSE over io_uring, Linux 6.14 (released 24 Mar 2025).** KernelNewbies: "This release adds FUSE support for io-uring communication between kernel and userspace." Kernel doc: per-CPU queues ("every CPU core has its own fuse-io-uring queue"), "still in development and might change". No performance numbers on the doc page. A later commit made it opt-in via sysfs (search summary only). https://kernelnewbies.org/Linux_6.14 and https://docs.kernel.org/filesystems/fuse/fuse-io-uring.html . Verified on page for those quotes.
- **LWN, 3 Aug 2026 (LSFMM+BPF 2026 report, Jake Edge):** discusses io_uring buffer sizes; Schubert says the aim is lower memory use, not speed; "The article gives no measured throughput." https://lwn.net/Articles/1085618/ . Verified on page.
- **Linux 7.3 (Aug 2026):** Phoronix, "Linux 7.3 FUSE Delivering Nice Performance Improvements" (26 Aug 2026): io_uring buffer pools and zero-copy, work by Joanne Koong; numbers are in a chart image. https://phoronix.com/news/Linux-7.3-FUSE . Secondary only (page returned 403; summary from search). Zero-copy requires CAP_SYS_ADMIN (kernel 7.3 doc page, search summary).
- **FSKit (macOS).** Apple DTS engineer on the Developer Forums (macOS 15.5): a read-only FSKit file system with hard-coded entries showed `getdirentries` at about 121 us per call; the engineer replied "It's reasonable in the sense that, yes, that's about where things stand at the moment", said "most of this is overhead of repeated XPC traffic, which probably could be avoided", and "the performance is definitely being looked at." https://developer.apple.com/forums/thread/793013 . Verified on page (it is a forum post, not Apple documentation). A second forum report of FSKit using 100-150% CPU against about 40% for macFUSE and an Apple reply that the read/write path is not optimised: secondary only (search summary, thread not opened). Conclusion: FSKit performance on macOS is documented as immature. No benchmark of FSKit against a kernel driver was found.
- **Windows SMB loopback performance:** no modern primary number found. The only source found is a 1999 research paper (FIFS, USENIX Windows NT Symposium) reporting about 70% of a kernel NFS implementation; too old to cite. A Microsoft SMB developer blog notes metadata operations go over the loopback connection, so a loopback share is not the same cost as a local path: https://learn.microsoft.com/en-us/archive/blogs/josebda/is-accessing-files-via-a-loopback-share-the-same-as-using-a-local-path (secondary only; seen in search summary).

### C3. Network file systems: does latency/cache dominate?

- **Direct evidence is thin.** No peer-reviewed study was found that compares a network file system client in FUSE against its in-kernel twin and shows the user-space penalty vanishing behind the network. The FAST 2017 result (HDD overhead negligible, SSD larger) supports the narrower point that slower back ends hide FUSE cost. A Red Hat Gluster presentation saying network and storage latency dominate was seen only in a search summary: secondary only.
- **Ceph:** only anecdotal. A Ceph tracker/mailing-list user (Nautilus 14.2, kernel 4.18) reported about 1.8 GB/s with the kernel client vs about 68 MB/s with ceph-fuse (dd test), a worst case from an old release; another developer reported about 3 GB/s per node with the kernel client vs 8 GB/s with libcephfs. Two March 2026 blog posts give percentages (kernel 20-30% faster) without a test setup. All secondary only. This cuts AGAINST the site's thesis for a fast cluster; say so, or leave Ceph out.
- **Mountpoint for Amazon S3:** GA 9 Aug 2023; AWS says "data transfer at up to 100 Gb/second between each EC2 instance and S3" (units are Gb, not GB). Written in Rust, a FUSE client (AWS docs describe "a Rust version of the Linux FUSE library"; the repo carries a fork of the `fuser` crate). SEMANTICS.md (verified on page): "Mountpoint does not implement all the features of a POSIX file system"; optional metadata and content caching with a default 1-minute metadata TTL. The 100 Gb/s figure and the GA date are secondary only (AWS pages returned only navigation text; figures from search summaries): https://aws.amazon.com/blogs/aws/mountpoint-for-amazon-s3-generally-available-and-ready-for-production-workloads/ . SEMANTICS verified: https://github.com/awslabs/mountpoint-s3/blob/main/doc/SEMANTICS.md . Default throughput target is 10 Gbps outside EC2 (search summary). This is a real, AWS-supported, production FUSE client reaching network line rate, which is the best evidence that FUSE is not the bottleneck on a network path. It is a vendor claim with no published methodology on the page I saw.
- **Cloud Storage FUSE (gcsfuse), Google:** "an open source FUSE adapter that lets you mount and access Cloud Storage buckets as local file systems." Google claims "up to 9x faster model load times" (parallel downloads, large single-threaded reads) and "up to 2.3x faster training time and 3.4x higher throughput observed in training runs", attributed to the local file cache. Vendor numbers, no methodology on the page; they show that caching, not the kernel/user boundary, drives the result. https://raw.githubusercontent.com/GoogleCloudPlatform/gcsfuse/master/README.md . Verified on page (README).
- **JuiceFS:** README: "JuiceFS is production ready and used by thousands of machines in production"; shared by "thousands of clients"; claims "10X more throughput" than EFS and S3FS; no FUSE-versus-kernel comparison. https://raw.githubusercontent.com/juicedata/juicefs/main/README.md . Verified on page. Weak as evidence for the performance claim.
- **Not found / not verified:** Meta or Google internal FUSE-at-scale papers with numbers; sshfs/rclone/s3fs numbers; GlusterFS FUSE vs kernel numbers (only the Red Hat slide, secondary); Lustre has no FUSE client comparison.

## Popular claims I could not verify
- "FUSE is 80% slower" without context: the real -83% is the unoptimised stack, SSD, 32 threads, small random reads, 2017; optimised was -28%, and the HDD case was negligible.
- "FUSE adds 4x latency": appeared only in a search summary of the FAST 2017 abstract text; not in the fetched abstract.
- "ENOTCONN means the app survives": the kernel FUSE doc does not mention ENOTCONN.
- "Microsoft requires antivirus to leave the kernel": the 2024-2026 posts describe previews, "can run in user mode", and DQI "moves toward user mode"; no hard mandate seen.
- Any submission turnaround time for Windows signing: not documented on the pages read.
- CSRB report on CrowdStrike: none found.
- Windows SMB loopback numbers: none found.
