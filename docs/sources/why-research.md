# Why user space: researched facts (2026-11-20)

"Verified on page" = text read in the fetched primary document (PDFs read via pdftotext). "Secondary" = search summary or news only.

## 1. Drivers and OS crashes

- **Drivers = 85% of reported Windows XP failures (2003).** Swift, Bershad, Levy, "Improving the Reliability of Commodity Operating Systems", ACM TOCS 23(1), 2005 (SOSP 2003 original). Abstract: "In Windows XP, for example, drivers account for 85% of recently reported failures." Intro: "drivers cause 85% of recently reported failures [Short 2003]". https://pages.cs.wisc.edu/~swift/papers/improving-reliability.pdf — verified on page.
  - **Real origin of the number:** the reference is "Short, R. 2003. Vice President of Windows Core Technology, Microsoft Corp. Private communication." So the 85% is a Microsoft VP's private communication, not a published Microsoft dataset. Say "reported failures", NOT "crashes" (the slide deck says "crashes"; the paper says "reported failures"). The figure was never found in a Microsoft publication.
  - Same paper: Nooks "eliminated 313 of 317 crashes observed with native Linux, or 99%" (fault injection). Verified on page. It also reports about 10% slowdown in one VFAT compile case. Verified on page.
  - Same paper also says "over 120,000 versions [of drivers] exist on Windows XP desktops [Short 2003]" (same private communication).
- **Microsoft's own doc, undated figure:** the Windows XP Embedded reliability page says third-party device drivers are "by a wide margin" the most significant cause of crashes, citing OCA (oca.microsoft.com). https://msdn.microsoft.com/en-us/library/ms838661(v=winembedded.5).aspx — secondary only (search summary, no number, page not opened).
- **Not found:** a later Microsoft WER/OCA percentage I could verify. Do not cite one.
- **Ganapathi, Ganapathi, Patterson, USENIX LISA 2006:** OS crashes on Berkeley volunteer machines were predominantly caused by poorly written device-driver code. https://www.usenix.org/legacy/event/lisa06/tech/full_papers/ganapathi/ganapathi_html/index.html — secondary only (search summary, not opened).

## 2. Driver bug density

- **Chou et al., "An Empirical Study of Operating Systems Errors", SOSP 2001.** Abstract: "device drivers have error rates up to three to seven times higher than the rest of the kernel." Body (Linux 2.4.1): drivers are "over 70%" of the code. They hold "over 90% of the Block, Free, and Intr bugs, and over 70% of the Lock, Null, and Var bugs". Driver code error rate is "almost three times greater than the rest of the kernel" for some checkers, and the Lock checker is "almost seven times higher". https://www.read.seas.harvard.edu/~kohler/class/aosref/chou01empirical.pdf — verified on page. Note: it is "up to", checker-dependent, and the code is Linux 1.0–2.4.1 plus OpenBSD.
- **Palix et al., "Faults in Linux: Ten Years Later", ASPLOS 2011, pp. 305–318.** Repeated Chou's study on Linux 2.6.0–2.6.33. Drivers are still the largest source of faults in absolute terms, but their fault rate is now below that of directories such as arch and fs, and faults per line decreased over the decade. https://pure.psu.edu/en/publications/faults-in-linux-ten-years-later/ — verified on page (paraphrase; direct quote not obtained). **Caveat for the site: this partly cuts against "drivers are buggiest" for 2011, so cite Chou for 2001 and do not claim it still holds.**

## 3. CrowdStrike, 19 July 2024

- **~8.5 million Windows devices, under 1% of all Windows machines.** Microsoft (David Weston), "Helping our customers through the CrowdStrike outage", 20 Jul 2024: "affected 8.5 million Windows devices, or less than one percent of all Windows machines". https://blogs.microsoft.com/blog/2024/07/20/helping-our-customers-through-the-crowdstrike-outage/ — verified on page. Microsoft said it was an estimate; the share is of all Windows machines, not of CrowdStrike customers.
- **The faulting component was a kernel driver.** Microsoft Security Blog, 27 Jul 2024, "Windows security best practices for integrating and managing security tools": csagent.sys is "registered as a file system filter driver"; CrowdStrike describes the root cause as a memory safety issue and Microsoft calls it a "read-out-of-bounds memory safety error" in the driver; analysis was based on kernel crash dumps. Also: "Kernel drivers provide the above properties at the cost of resilience." https://www.microsoft.com/en-us/security/blog/2024/07/27/windows-security-best-practices-for-integrating-and-managing-security-tools/ — verified on page.
- **Trap:** CrowdStrike says "Although Channel Files end with the SYS extension, they are not kernel drivers." The channel file C-00000291*.sys was a content file, released 04:09 UTC and online-affected window 04:09–05:27 UTC; the kernel driver crashed reading it. https://www.crowdstrike.com/blog/falcon-update-for-windows-hosts-technical-details/ — verified on page. Do not write "a bad driver file was pushed".
- **CrowdStrike RCA (6 Aug 2024):** template type defined 21 input fields but the integration code supplied 20, so there was an out-of-bounds memory read (no runtime bounds check). https://crowdstrike.com/wp-content/uploads/2024/08/Channel-File-291-Incident-Root-Cause-Analysis-08.06.2024.pdf — secondary only (search summary; PDF not opened).
- **Windows Resiliency Initiative, 19 Nov 2024.** Weston, Windows Experience Blog: Microsoft is "introducing the Windows Resiliency Initiative, covering four areas of focus" (reliability improvements from "the July incident"; fewer admin privileges; stronger app/driver controls; identity protection). Security products "can run in user mode just as apps do"; private preview for the security ecosystem planned July 2025. https://blogs.windows.com/windowsexperience/2024/11/19/windows-security-and-resiliency-protecting-your-business/ — verified on page. The post does not name CrowdStrike.
- Mid-2025 trade-press reports of the Windows endpoint security platform preview for MVI partners (CrowdStrike, ESET, etc. named): secondary only. Not checked: whether it shipped in general availability by Nov 2026.

## 4. Apple

- **Kext deprecation.** Apple: "As part of our ongoing effort to modernize the platform, improve security and reliability, and enable more user-friendly distribution methods, kernel extensions have been deprecated." Also: system extensions allow software to extend macOS "without requiring kernel-level access"; "Starting with macOS Big Sur, macOS releases no longer load kernel extensions that use deprecated kernel programming interfaces (KPIs) by default." https://developer.apple.com/support/kernel-extensions/ — verified on page. Many KPI families are listed as deprecated in Catalina 10.15 and unsupported in Big Sur 11.0. The page does NOT state a blanket "all kexts deprecated in 10.15". Safer wording: "from macOS Catalina (2019) Apple deprecated kext KPIs in favour of system extensions".
- **WWDC19 session 702 (2019):** "One of the next steps in modernizing and improving the security and reliability of macOS is to provide a better architecture for kernel extensions and drivers. Learn how to make this transition with System Extensions and DriverKit." https://developer.apple.com/wwdc19/702 — verified on page.
- **FSKit.** macOS Sequoia 15.4 release notes: "FSKit is now available, enabling delivery of user space file systems as Application Extensions. These file systems support integration with DiskArbitration." https://developer.apple.com/documentation/macos-release-notes/macos-15_4-release-notes.md — verified on page. 15.4 shipped March 2025. Note: FSKit was in 15.4 only for block-device-backed volumes; macOS 26 added URL-resource support (forum report, secondary). Apple docs: only FSUnaryFileSystem (secondary).
- **macFUSE 5.0.0 (5 May 2025)** added an opt-in FSKit backend; **5.1.0 (30 Oct 2025)**: "When specifying the mount option `-o backend=fskit`, `libfuse3` will use the `FSKit` backend"; adds non-local volumes on macOS 26. https://macfuse.github.io/2025/10/30/macfuse-5.1.0.html — verified on page.
- **Eclectic Light (18 Nov 2025):** FAT and exFAT "In recent versions of macOS, these file systems are implemented in user-space using FSKit"; native file systems are traditionally "in kernel-space, requiring a kernel extension". https://eclecticlight.co/2025/11/18/which-local-file-systems-does-macos-26-support/ — verified on page (blog, secondary for Apple facts).

## 5. Linux

- **FUSE in mainline 2.6.14.** Linux 2.6.14 released 27 October 2005; FUSE: "Allows to implement a fully functional filesystem in a userspace program". https://kernelnewbies.org/Linux_2_6_14 — verified on page. Kernel docs: "FUSE is a userspace filesystem framework. It consists of a kernel module (fuse.ko), a userspace library (libfuse.*) and a mount utility (fusermount)." https://docs.kernel.org/filesystems/fuse/fuse.html — verified on page.
- Szeredi 2005 pre-merge note: about 7,000 downloads in three months, 27 known userland filesystems, 7 language bindings. https://lkml.indiana.edu/hypermail/linux/kernel/0509.0/0678.html — secondary only (search summary).
- **No stable in-kernel interface.** kernel docs, "The Linux Kernel Driver Interface" (stable-api-nonsense): the kernel "does not have a binary kernel interface, nor does it have a stable kernel interface"; this is about in-kernel interfaces, while the syscall interface is "very stable over time, and will not break". Changes: "function names may change, structures may grow or shrink, and function parameters may be reworked." In-tree: "If your driver is in the tree, and a kernel interface changes, it will be fixed up". https://www.kernel.org/doc/html/latest/process/stable-api-nonsense.html — verified on page. Not found: a number on how many out-of-tree modules break per release; no such statistic cited.
- Notable production user-space file systems: not researched or verified in this pass (no source cited).

## 6. Windows user-space options (facts only)

- **ProjFS:** "allows a user-mode application called a 'provider' to project hierarchical data from a backing data store into the file system". Example provider: VFS for Git, "used to virtualize very large git repos". Designed for high-speed backing stores; for slow ones Microsoft points to the Cloud Files API. https://learn.microsoft.com/en-us/windows/win32/projfs/projected-file-system — verified on page.
- **Cloud Files API:** introduced in Windows 10 version 1709 (Fall Creators Update). The sync engine runs in user mode, but "at the core of the storage stack ... is a file system minifilter driver called cldflt.sys", which proxies between applications and the sync engine; supports NTFS volumes only. https://learn.microsoft.com/en-us/windows/win32/cfapi/build-a-cloud-file-sync-engine — verified on page. Note that this still has a Microsoft-supplied kernel minifilter; the third party's code is in user mode.
- **SMB loopback:** no source fetched; do not state facts.

## Claims NOT verifiable at the source
- "85% of Windows XP crashes are caused by drivers": the source is a private communication from a Microsoft VP, and the paper says "failures", not "crashes".
- A blanket "kexts deprecated in Catalina 10.15": Apple's page ties deprecation to specific KPIs in 10.15 and enforcement in Big Sur 11.0.
- Any later Microsoft WER-based driver crash share: none found.
- "Drivers are 7x buggier": the actual wording is "up to three to seven times" (2001), and Palix 2011 says drivers' fault rate had dropped below arch and fs.
- CrowdStrike "kernel driver update": the update was a content/channel file read by the kernel driver.
- AFS-specific examples: skipped per courtesy rule.
